# F09 — Git LFS contract

Status: Defined for implementation; not yet conformance-tested. Revision 1, 2026-10-18.

## Client and protocol baseline

Git LFS batch API using basic HTTP transfer, SHA-256 object IDs, upload verification and range downloads.

- git-lfs: **v3.8.0** ([release/source](https://api.github.com/repos/git-lfs/git-lfs/releases/latest)).

Pin actual downloaded artifact digests in the conformance fixture lock; these are deliberately selected baseline versions, not a promise of all historical or future clients.

## Publish / ingest

git lfs push uses batch upload actions bound to object identity and scoped credentials; verify size/hash before advertising existence.

## Consume and source support

git lfs pull/fetch batch requests return authorized local/proxy/replica object URLs.

## Resolution policy

object-owner per LFS oid within feed

## Format-specific integrity and metadata

Object authorization must not be inferred from global blob existence; action URLs expire and cannot leak credentials across origins. Ordinary Git metadata lives in the user Git server.

## Explicit non-goals

LFS locking and custom transfer adapters are excluded initially; this is not a Git hosting service.

## Required client scenarios

- [ ] Push then pull a large object with pinned oid; resume download from a fresh authorized batch response.
- [ ] Wrong size/hash and expired action URL fail; an inaccessible deduplicated object cannot be enumerated.

All [shared source, cache, auth, lifecycle, search, replication and conformance requirements](common.md) also apply. Task T1 closes contract definition only; T2–T4 remain implementation and evidence work.
