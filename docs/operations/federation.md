# Federation (Phase 2)

Federation groups independently operable Kuvryn Ant instances under one signed, versioned membership. Delivered: founding, invitations, join, leave, suspend, resume, remove, membership sync and status (P2-M1), shared identity and policy with principal assertions (P2-M2), coordinated replication with feed homes and home transfer (P2-M3), cross-instance search (P2-M4) placement-aware read routing (P2-M5), and operations (P2-M6): planned authority handover and forced recovery, federated audit, the recovery-key drill, two-phase join and revocation pruning ([runbooks](federation-runbooks.md)). See [the design](../planning/phase-2-federation.md).

Serving never depends on federation. A federation listener that cannot bind, an unreachable authority, or a rejected document is logged, shown as `degraded` in federation status, and the instance keeps serving with the last applied membership. Readiness probes never fail because of federation.

## Configuration

| Variable                    | Purpose                                                                                                                                                                                                                                |
| --------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| `ANT_FEDERATION_LISTEN`     | Address of the dedicated mTLS listener, for example `0.0.0.0:8444`. It is a separate server and is never mounted on the public HTTP listener. Unset means no listener.                                                                 |
| `ANT_FEDERATION_PUBLIC_URL` | `https://host:port` other members use to reach the listener. Required to found or join. The member certificate's SAN is this host.                                                                                                     |
| `ANT_FEDERATION_JOIN_DIR`   | Optional directory (a mounted Secret) with files `authority_url`, `ca_sha256`, `invitation` and optionally `authority_cert_sha256`. An instance that was never federated joins automatically at startup and retries until it succeeds. |

Federation keys (CA, authority signing key, member keys) are stored encrypted in PostgreSQL under the root key (`internal/secrets`, purposes `federation-ca`, `federation-authority:<epoch>`, `federation-member-key`). Back up the root key as before; no new secret material is mounted.

Helm: set `federation.enabled`, `federation.publicURL` and `federation.service` (LoadBalancer, NodePort or ClusterIP). TLS must reach the pod unterminated: use the federation Service directly, or `federation.ingressPassthrough` with ingress-nginx `--enable-ssl-passthrough`. `federation.join.existingSecret` enables automatic join, and `federation.networkPolicyFrom` opens the port to the other members when `networkPolicy.enabled` is set. A member must be reachable by name from every member that initiates traffic to it (status pings, nudges, search and proxied reads, replication from a feed home): `hostAliases` (chart value) gives a pod the address of a member whose federation name only its own site resolves, and a ClusterIP federation Service needs a LAN-reachable companion (`deploy/examples/kw-federation-lan.yaml`). The examples in `deploy/examples/` contain commented federation sections.

### Federation through a shared Gateway API gateway (OKE)

Set `federation.tlsRoute.enabled`, `.hostname` and `.parentRefs` (gateway plus the TLS Passthrough listener `sectionName`) to publish the federation port through a shared Envoy Gateway instead of a dedicated LoadBalancer; the chart then renders a `TLSRoute` to the federation Service, and `federation.service.type` can be `ClusterIP`. The gateway listener must use protocol TLS, mode Passthrough, so mTLS still ends in the pod. The OCI load balancer does not preserve client IPs: restrict the source allowlist in the OCI security list for the listener port, not in Envoy. OKE runs this way: `ant-federation.azrty.com:8444` resolves to the edge IP, and rollback is to re-enable the LoadBalancer Service and point DNS back at its address.

## Procedures

All operations are available in the console (Federation page) and the management API (`/api/v1/federation…`, see `api/openapi.yaml`). Reads need `read` on the instance; changes need instance `admin`. MCP exposes `get_federation_status` and `list_federation_members`.

1. **Found** on the intended authority: `POST /api/v1/federation {"name":"watteel","member_name":"oke"}`. The response contains the **recovery key once**. Store it offline (password manager or sealed envelope). It is never stored on the instance and is required for forced authority recovery and for rotating the recovery key. Note the CA fingerprint (`ca_sha256`).
2. **Invite** on the authority: `POST /api/v1/federation/invitations {"name":"kw","labels":{"site":"kw"}}`. The secret is shown once and expires after one hour by default (`ttl_seconds`, at most 7 days). Hand the authority URL, CA fingerprint, authority certificate fingerprint and secret to the joining administrator out of band.
3. **Join** on the new member: `POST /api/v1/federation/join {"authority_url":…,"ca_sha256":…,"authority_cert_sha256":…,"invitation":…}`. The connection is pinned to the CA fingerprint; the system trust store is not used. `authority_cert_sha256` (from the invitation, recommended) also pins the authority's certificate before the invitation is sent. In every case the member verifies the whole signed membership chain and refuses an answer from a server whose certificate is not the one membership publishes for the authority, so another member's CA-issued certificate cannot relay or intercept the join. The authority refuses a member whose federation URL host is already used by another member (loopback hosts are compared with their port, for single-machine labs). For automatic join, `ANT_FEDERATION_JOIN_DIR` may also contain `authority_cert_sha256`.
4. **Leave** on a member: `POST /api/v1/federation/leave {"confirm":true}`. The authority removes the member and revokes its certificate. Content and local configuration are kept. `force: true` leaves locally if the authority is unreachable. The authority cannot leave: hand the role over first (Authority operations below).
5. **Suspend / resume / remove** on the authority: `POST …/members/{id}/suspend|resume`, `DELETE …/members/{id}?confirm=true`. Suspended and removed members are refused on every listener once the new membership is applied; removal also revokes the certificate serial.
6. **Rotate the recovery key** without sending any recovery private key to a server. The signing commands run offline (no database, no network: use an air-gapped machine where the key is kept):
   1. On the authority: `GET /api/v1/federation/recovery-key/rotation` and save the response as `template.json` (federation ID, the membership generation the rotation will be published at, the current recovery public key and the authority certificate to re-certify).
   2. Offline: `ant federation recovery sign-rotation --template template.json --key current.key --new-key-out new.key > rotation.json`. It checks that `current.key` matches the template, generates the new recovery key into `new.key` (created with mode 0600, never overwritten) and signs the rotation statement with the current key.
   3. Offline: `ant federation recovery sign-authority-cert --template template.json --key new.key --rotation rotation.json > request.json`. It certifies the current authority key with the new recovery key and merges both statements into the request body.
   4. On the authority: `POST /api/v1/federation/recovery-key/rotate` with `request.json` (`{"rotation":…,"authority_certificate":…}`). The authority verifies both signatures and publishes them in the next membership generation; every member verifies the rotation against the previous recovery key. If the membership moved on after step 1 the call answers `409 stale_generation`: fetch a new template and sign again. Key files hold the `ant-recovery-v1:` export; keys are never accepted as arguments or on standard input. Store `new.key` offline and destroy the old key once the new generation is applied.

Members poll the authority every 30 seconds and receive signed nudges after each change. If the authority is unreachable they fetch documents from any other active member; documents are self-authenticating, so relays cannot alter them. Keys and signatures are accepted only in canonical unpadded base64url, so a signature has exactly one spelling and a relay cannot fork the hash chain by re-encoding it. A member whose membership, policy or topology chain still diverges from the authority (a `prev_hash` mismatch on the next generation, or the same generation with another hash) recovers by a snapshot resync from the authority (§6.4 rule 6): it verifies the authority chain from the last shared generation and replaces the divergent segment in one transaction, audited as `federation.document.resynced`; the applied generation never moves backwards.

## Status and alerts

`GET /api/v1/federation/status` reports state, role, epoch, applied generation and its age (time since membership was last confirmed current), member certificate expiry, last sync time, source and error, and member counts. `GET /api/v1/federation/members` adds per-member RTT, clock skew and last-seen time. Metrics: `ant_federation_active`, `ant_federation_document_generation{kind}`, `ant_federation_authority_epoch`, `ant_federation_members{status}`.

Alert when health is `degraded` for more than 15 minutes (critical after 24 hours). Audit events: `federation.created`, `federation.joined`, `federation.left`, `federation.member.added|left|removed|suspended|resumed`, `federation.invitation.created|revoked|rejected`, `federation.document.published|applied|rejected|resynced`, `federation.peer.rejected`, `federation.certificate.issued|renewed|retired`, `federation.recovery_key.rotated`. Rejections are recorded with result `denied`.

Requirements: NTP on every member (signed requests are rejected beyond 60 seconds of clock skew), and a reachable federation port between members. Member certificates last 30 days and renew automatically after two thirds of their lifetime.

## Security controls

- **Join endpoint.** `POST /federation/v1/join` is the only unauthenticated peer route. It is rate-limited per remote IP (burst 10, then one request every 6 seconds; `429 rate_limited`), and the invitation is verified before the authority takes its federation state lock, so invalid invitations cannot stall federation changes. Refusals count in `ant_federation_join_rejected_total`; `federation.invitation.rejected` audit records are throttled to one per reason every 10 seconds and carry the number of suppressed refusals (`suppressed`).
- **Certificate pinning.** Peers accept a member only with the certificate fingerprint published for it in membership (`cert_sha256`): a certificate the federation CA issued for the same instance ID but not published is refused (`403 certificate_not_current`). After a renewal the previous certificate stays accepted for 24 hours (`previous_cert_sha256`, `previous_cert_until`); the authority then revokes its serial in a new generation (`federation.certificate.retired`). A renewal CSR must use the key of the certificate the member authenticated with, or carry that key's signature over the CSR (`csr_signature`), so a stolen certificate cannot be renewed onto another key (`403 csr_key_mismatch`). A nudge from a renewed authority is accepted once the membership it carries publishes the new fingerprint.
- **Request limits.** Signed peer requests on every route (documents, search, replication export) are rate-limited per member (200 per second, burst 400; `429 rate_limited`). Request nonces are remembered per member for 5 minutes, at most 65536 per member (beyond that the member is refused rather than the cache growing), and expire in insertion order without scanning. Assertion replay records (`federation_assertion_nonces`) are capped at 20000 unexpired records per issuing member (`429 rate_limited`) and expired records are purged in batches on every worker cycle.
- **Canonical numbers, IDs and CA.** Signed documents and statements refuse numbers beyond 2^53 - 1 (they cannot be canonicalized unambiguously; plain RFC 8785 canonicalization is unchanged). A receiving member derives the federated ID of an asserted principal itself and ignores the issuer's claim. Federation CAs created from this release on are name-constrained (no e-mail or URI names) and limited to TLS server and client use; existing CAs are unchanged until CA rotation.

## Shared identity and policy (P2-M2)

The authority publishes a signed, versioned **policy document** on the same envelope and hash chain as membership: identity domains (trusted issuers), federated roles (keys start with `fed:`) with grants on feed keys (`<federation>/<feed-slug>`), principal bindings, group bindings, federated service accounts and revocations. Every member verifies and applies it locally; the evaluator is unchanged (deny wins, union of allows).

- **Publish** on the authority: `PUT /api/v1/federation/policy/draft {"policy":{…}}` (validated, diff against the applied generation), then `POST /api/v1/federation/policy/publish {"base_generation":N,"confirm":true}` (or include `policy` inline). A stale `base_generation` answers `409 stale_generation`. Members are nudged and otherwise pick it up on their next poll (relays from any member work). History and diffs: `GET /api/v1/federation/policy`, `GET /api/v1/federation/policy/diff?from=&to=` (`to=draft`), `GET /api/v1/federation/documents/policy/{generation}`.
- **Bind feed keys** on each member: `POST /api/v1/federation/feed-bindings {"feed_key":"lab/release","feed_id":…}`. Grants on a key that is not bound stay inert (never a wildcard) and are listed as unresolved in status; binding activates them, deleting the feed or unbinding makes them inert again.
- **Local overrides** (member admin, never the authority): local deny roles beat federated allows, local allows add to federated ones, and federated denies beat local allows. Federated instance-admin allows, and artifact or feed allows without a feed key (they would match every local feed, federated or not), are inert until `PUT /api/v1/federation/settings {"accept_admin_grants":true}` (reported together as `inert_admin_grants`; the grants show `inert: admin_not_accepted` or `wildcard_not_accepted`). Federated denies without a feed key always apply. Federation-managed roles, grants, memberships and principals are read-only locally (`409 federation_managed`); local roles can still be assigned to federated principals. A binding that matches an existing local principal is reported as `conflict_local_principal` until `POST /api/v1/federation/principals/{id}/adopt {"confirm":true}`.
- **Principals.** Federated service accounts are materialized on every member (tokens stay local: issue them per member). Federated users are materialized when bound or at their first sign-in through a matching identity domain; group bindings are evaluated against the groups of the last sign-in (OIDC `groups` claim, SAML Groups, LDAP immutable group IDs). Revocations disable the principal and revoke its local tokens and sessions on apply. Leaving the federation removes federation-managed roles and grants; principals stay as local principals with their local roles.
- **Assertions.** Cross-member requests carry a signed, 60-second, request-bound assertion on the mTLS listener; replays are refused through `federation_assertion_nonces` and skew beyond 60 seconds is refused. `POST /api/v1/federation/access-check {"member_id":…,"kind":"feed","feed_key":…,"action":"read"}` asks another member for its own decision for the calling federated principal (local principals get `403 not_federated`).
- **Stale policy (D4).** Members keep enforcing the last known good policy when the authority is unreachable or a document is rejected (forged, tampered, stale, gap): rejections are audited (`federation.document.rejected`, kind `policy`) and shown in status. Alerts `policy_stale` (warning after 15 minutes, critical after 24 hours without confirmation), `policy_rejected`, `membership_stale` and `policy_conflicts` appear in `GET /api/v1/federation/status` (`alerts`), mark health `degraded` (never unready), are exported as `ant_federation_alert{code,severity}` and raised/cleared once per transition as `federation.alert.raised` / `federation.alert.cleared` events (webhooks and audit sinks deliver them). The optional hard limit `policy_max_age_seconds` (default off) denies federated principals beyond it; local principals are unaffected.

MCP: `get_federation_policy`, `list_federated_principals`, `check_federation_access` and the destructive `publish_federation_policy` (`confirm: true`); resources `ant://federation`, `ant://federation/members`, `ant://federation/policy`. Metrics add `ant_federation_document_generation{kind="policy"}`, `ant_federation_document_age_seconds{kind="policy"}`, `ant_federation_policy_unresolved_feed_keys` and `ant_federation_assertions_total{outcome}`. Audit adds `federation.policy.applied|draft_saved`, `federation.principal.materialized|revoked|restored|adopted`, `federation.feed.bound|unbound`, `federation.settings.updated`, `federation.assertion.accepted` (sampled) and `federation.assertion.rejected`.

## Offline maintenance

Run with the serving process stopped (both refuse while the writer lease is held):

- `ant federation status` prints the local federation view from the database.
- `ant federation recovery sign-rotation|sign-authority-cert` sign a recovery-key rotation offline (see Procedures, step 6); they need neither the database nor the serving process.
- `ant federation re-identify --confirm` gives a restored copy of an instance a new instance ID (every UUID column holding the old ID is rewritten in one transaction, encrypted secrets are re-sealed under the new ID) and resets its federation state to none, so it can join with a new invitation instead of being refused as a duplicate. Update `ANT_INSTANCE_ID` if it is set.
- `ant federation purge --confirm` deletes all federation rows (state, documents, members, invitations, drafts, bindings, federation keys) of an instance that left or was removed, so a binary downgrade sees no federation data. It is irreversible.

## Cross-instance search (P2-M4)

`GET /api/v1/federation/search?q=&format=&namespace=&digest=&feed_key=&members=&limit=&cursor=` searches this member and fans out to the other active members over the peer listener (`POST /federation/v1/search`) with a signed, request-bound, replay-protected assertion of the caller. Each member applies its own policy (including local overrides and token scopes) to the asserted principal, so a caller sees only what each member allows. Only feeds bound to a federation feed key take part; only federated principals can search (`403 not_federated` otherwise). `digest=sha256:<hex>` is the checksum lookup.

- Limits: concurrency 8, 1.5 s per member, 2 s overall; a member over its deadline, unreachable or refusing never fails the query. `members[]` reports `ok|timeout|error|skipped` with a code (`deadline`, `unreachable`, `rate_limited`, `no_identity`, peer codes), `took_ms` and hit counts; `partial` is true when any member is not ok.
- Merge: hits are merged on `(feed_key, coordinate)`, ordered bytewise. Replica copies collapse under the home copy in `copies[]`. Pagination uses one watermark on that key that every member honors, wrapped in this member's authenticated cursor (tampering, another query or another member's cursor is `400`).
- Abuse controls: per-peer 50 req/s and per-asserted-principal 20 req/s on the receiving member (`429 rate_limited`); remote answers are cached 30 s per `(member, principal, token scopes, query, policy generation)` and the cache is dropped when policy is applied. Local role changes on a member can therefore take up to 30 s to show in a repeated identical query.
- Metrics: `ant_federation_search_requests_total`, `ant_federation_search_partial_total`, `ant_federation_search_cache_hits_total`, `ant_federation_search_rate_limited_total`. MCP: `federated_search`, `federated_lookup_checksum`. Console: Packages, scope toggle "This instance" / "Federation" (shown on active members).
- P2-M4 deviations: targets are all active members (topology-based target selection and `home`/`replica_lag_seconds` from descriptors arrive with P2-M3; `home` is derived from the owning source kind, `replica` meaning not home); no migration was needed.

## Coordinated replication (P2-M3)

The authority publishes a third signed document kind, **topology**, on the same envelope and hash chain as membership and policy. It records federated feeds (feed key `<federation>/<slug>`, its single **home** member, a non-secret descriptor with format and anonymous-read default, and the home-transfer state) and **replication rules**. Members verify, apply and relay it exactly like policy (`federation.document.applied|rejected`, kind `topology`; last known good on rejection, alert `topology_rejected`).

- **Feed keys** (authority): `POST /api/v1/federation/feeds {"feed_key":"watteel/npm","home_member_id":…}`. One home per key; a second claim answers `409 feed_home_elsewhere`. When the authority is the home, the descriptor is taken from its bound feed. `DELETE /api/v1/federation/feeds/{fed}/{slug}` removes a key without rules or an active transfer. The home member binds its feed to the key (`POST /api/v1/federation/feed-bindings`).
- **Rules** (authority): `POST /api/v1/federation/replication/rules {"feed_key":…,"targets":{"labels":{"site":"kw"}}}` (or `{"members":[…]}`), with `mode`, `interval_seconds`, `include_cached`, `filters`, `deletion_policy`, `destination_read_only`, `create_destination_feed`, `adopt_existing`, `max_lag_seconds`. Defaults: continuous, 300 s, include cached, ignore deletions, read-only destination, create the destination feed, adopt existing jobs, 900 s lag budget. `PATCH …/rules/{id}` needs the revision (`If-Match "N"` or body `revision`); `DELETE` releases the targets' jobs. A rule cannot explicitly target the home member; label targets simply skip it.
- **Reconciler** (every member, under the writer lease, after every topology apply and every 30 s): for each rule that targets it, it ensures the destination feed (the bound feed; or, with `create_destination_feed`, a new feed from the descriptor when no feed with that slug exists; an existing unbound feed is never taken over), a federation-mode peer for the home member (`fed-<member>`, `auth_mode=federation`) and one job with `origin=federation`. Rule changes are patched onto the job (filters affect future changes only). A removed rule disables the job and releases it to `origin=local`; content and replica source stay. Federation-managed jobs and peers are read-only through `/api/v1/replication/…` (`409 federation_managed`); manual runs are allowed.
- **Transport:** federation-mode jobs pull over the federation mTLS listener (`/federation/v1/replication/export/feeds/{feed}/…`, the same wire format as the bearer export API) with the member certificate and request signature; no peer token. The home serves a feed only to members a rule for its key targets (or the other side of its transfer), decided from the applied topology. Token-mode peers keep working for non-members.
- **Adoption without reseed:** an existing local job that already replicates the home feed (its peer is the home member, or a token peer whose URL is the home's API URL, and its remote feed is the home feed) into the bound feed is adopted in place: origin, rule and peer switch to federation, checkpoint, phase, counters and replica source do not. With `adopt_existing` (default) the reconciler does it; otherwise `POST /api/v1/federation/replication/adopt {"job_id":…,"rule_id":…}` (instance admin on the member) does it explicitly and refuses jobs that do not match.
- **Status:** `GET /api/v1/federation/topology` (feed keys, homes, transfers, rules, local role and freeze per key), `GET /api/v1/federation/replication/status` (rules targeting this member: state `in_sync|lagging|seeding|failed|pending|missing_feed|conflict|disabled`, job, phase, lag, adopted; quarantines), `GET /api/v1/federation/replication/rules/{id}/compliance` (the rule on every target, asked over mTLS; unreachable members are `unknown`). Federation status adds a `topology` summary.

### Home transfer (D6)

`POST /api/v1/federation/feeds/{fed}/{slug}/transfer {"to_member_id":…,"mode":"planned"|"forced","confirm":true}` on the authority. The target must be an active member that a rule for the key targets (it holds a replica). One transfer per key at a time (`409 feed_transferring`). The authority drives it from its reconcile loop:

1. **planned** – `freeze`: the home applies the generation, freezes the feed (publishes and deletes answer `503 feed_transferring`) and records its change head. `drain`: the target's job reaches the frozen head (the target triggers runs). `promote`: the target converts the job's replica source into a local source in one transaction (provenance kept, job removed, feed writable, new change baseline). `complete`: topology names the new home; the old home **demotes**: its local source becomes the replica source of a federation job on the new home, its assets are re-stamped with that job's provenance and the job starts with a manifest walk that deduplicates every blob, so nothing is transferred again. Freeze and drain abort on `drain_timeout_seconds` (default 900) or `POST …/transfer/abort {"confirm":true}`; the home unfreezes. Promotion cannot be aborted.
2. **forced** (`accept_data_loss: true`) – for a lost home: skips freeze and drain and promotes the target immediately. An old home that returns fences itself while applying the generation (freeze in the same transaction, before it accepts another write), detaches its local sources as **quarantined** sources with the number of changes after the target's checkpoint, and seeds a fresh replica from the new home. Nothing is merged. Alert `feed_home_conflict` (critical) stays until `POST /api/v1/federation/quarantines/{id}/resolve {"confirm":true}`; the quarantined source stays until deleted.

Other members re-point their jobs to the new home with a restartable manifest walk (blobs already present are deduplicated; items the new home no longer lists become held deletions). A demoted home's publish target is removed (it was the converted source); the removed default and rules are recorded in the transfer step.

MCP: `get_federation_topology`, `list_replication_rules`, `get_replication_rule_compliance`, `get_federation_replication_status`, `set_replication_rule`, `adopt_replication_job` and the destructive `start_feed_transfer` (`confirm: true`); resource `ant://federation/topology`. Metrics add `ant_federation_document_generation{kind="topology"}`, `ant_federation_topology_rules_targeting_self`, `ant_federation_topology_home_feeds`, `ant_federation_transfers_active` and `ant_federation_quarantines_unresolved` (per-job lag stays in `ant_replication_*`). Audit adds `federation.feed.created|deleted|created_from_descriptor`, `federation.replication.rule_created|rule_updated|rule_deleted`, `federation.replication.job_created|job_adopted|job_updated|job_released|job_repointed`, `federation.transfer.started|frozen|unfrozen|fenced|advanced|promoted|demoted|quarantined|aborted` and `federation.quarantine.resolved`.

Leaving the federation releases federation jobs to origin local (jobs on federation-mode peers are disabled) and clears freezes and home records; content is untouched.

## Placement-aware routing (P2-M5)

A read (GET or HEAD) of a federated feed that this member is not the home of is answered locally first when a local feed is bound to the key (a replica). A local 404, or a feed key without a local feed (the client uses `/feeds/<key-slug>/<format>/…` or `/v2/<key-slug>/…` on any member), is routed to a member that holds the key. Writes are never routed (D6): publishes and deletes are answered locally (the replica denial or feed not found) with `Ant-Feed-Home: <home feed endpoint>`, and the holder's proxy endpoint refuses every non-read method with `405 writes_not_routed`.

- **Candidates** are the active members holding the key: replicas (members a rule for the key targets) first, the home last as the authoritative fallback. Replicas whose replication state is not `in_sync` (or whose lag exceeds the routing `max_lag_seconds`) are skipped; a replica whose state is not reported yet is tried after in-sync ones. Among the rest: label preference (`prefer`), replica state, then the RTT EWMA from status pings and proxied requests. At most four members are tried per read; a 404 or a refusal moves on, so a member that lacks the content (or denies the caller under its own policy) never ends the search. All holders 404: the entry member answers 404. Every holder down, lagging or excluded: `503 route_unavailable` with `Retry-After`.
- **Circuit breaker:** three consecutive failures (pings or proxied requests) open a member's circuit for 30 s, doubling up to 4 minutes while it keeps failing; after the open period one request is a half-open trial, and a success closes it.
- **Proxy** (default, D5): the request goes over the mTLS listener to `/federation/v1/proxy/feeds/{fed}/{slug}/…` with a signed assertion of the caller bound to the request. The holder applies its own policy (local overrides, token scopes) and answers from its own content through its unwrapped adapters (a proxied read is never routed again). Range, conditional, `Accept` and `User-Agent` headers pass through; credentials, cookies and client addresses do not. The answer streams with a 32 KiB buffer under a transfer budget of 64 concurrent proxied reads per entry member (`503 route_busy` beyond), of which one principal may hold 8 and one client address 16 (`429 route_busy` beyond). After a 30 s grace period a transfer must keep an average of at least 16 KiB/s, and it ends after 2 hours: a client that stops reading, or a holder that stops sending, loses its slot (the transfer is aborted, never shown complete). Client cancellation cancels the upstream request. Proxied answers carry `X-Content-Type-Options: nosniff` and `Content-Security-Policy: sandbox`; the holder's cookies, authentication challenges, CORS (`Access-Control-*`, `Cross-Origin-*`), hop-by-hop (including headers it names in `Connection`) and browser-policy headers (CSP, HSTS, `Clear-Site-Data`, `Refresh`, ...) are dropped. Feed URLs in textual metadata (JSON, XML, YAML, text) and in `Location`/`Link` headers are rebased from the holder's API URL and feed slug onto this member's; content-addressed documents (OCI manifests, anything with `Docker-Content-Digest`, compressed or partial bodies) are never rewritten. Anonymous callers are asserted as anonymous only when this member's instance-wide client policy allows anonymous reads without a network restriction, and the holder serves them only for its own `anonymous_read` feeds with the same condition. Only federated principals (and anonymous callers) can be routed; a local principal gets the local answer with `X-Kuvryn-Route: not_federated`. Directory passwords are verified only for local feeds: reaching a feed this member does not hold needs a token or a browser session.
- **Redirect** (opt-in): `307` to the first candidate's public feed endpoint (`<api_url>/feeds/<its slug>/…`). The client must authenticate there on its own (anonymous feeds, or credentials valid on the holder). Only an entry member without a local copy {"mode":"proxy|redirect|off","blob_urls":false,"blob_url_bind_client":false,"cache":false,s; a replica that misses proxies, so redirects never chain.
- **Signed blob URLs** (opt-in in proxy mode, `blob_urls`): digest-addressed reads only (OCI blobs and manifests by digest) get a `307` to `<holder api_url>/federation/blob/<name>?k=<key>&p=<path>[&b=ip]&t=<ticket>` on the holder's public listener. Every other path (npm tarballs, raw files, Maven artifacts, package archives) is proxied: its bytes can change behind the name. The ticket is the caller's assertion signed by the entry member, bound to the key and path, for the holder only, valid five minutes. The holder authorizes the bytes itself: it re-authorizes the caller under its own policy, serves only an asset of the bound feed with the digest in the path (`404` otherwise) and refuses an answer with another `Docker-Content-Digest`; a path-scoped ticket is refused with `403 blob_url_not_immutable`. With `blob_url_bind_client: true` the ticket is also bound to the client address the entry member saw (`b=ip`), and the holder refuses it from any other address; both members must resolve the same client address (direct clients, or `ANT_TRUSTED_PROXIES` covering the ingress on both). Tickets can be used repeatedly within their lifetime (clients retry and resume). The holder removes `k`, `p`, `t` and `b` from the request before anything downstream logs or traces it and answers with `Referrer-Policy: no-referrer`; configure an ingress in front of the holder not to log query strings of `/federation/blob/`.
- **Entry cache** (opt-in in proxy mode, `cache`): a member with a feed bound to the key keeps complete, length-checked immutable proxied answers in its storage (`federation_route_cache`, dedup domain `federation-route-cache`) for `cache_ttl_seconds` (default 86400) and serves them only to callers its own policy lets read the whole local feed. Digest-addressed answers (OCI blobs and manifests by digest, verified against the digest while they stream) are served as stored. Any other answer is stored only with a strong `ETag` and revalidated with a holder on every hit (`If-None-Match`): `304` serves the cached bytes (`X-Kuvryn-Route: cache; revalidated; member=<name>`), `200` streams and replaces them, a `404`/`410` from the home drops the entry, and without a reachable holder the read answers `503` instead of the cached copy. Deletes replicated from the home drop every entry of the feed; package metadata changes (yanks, deprecations) drop every entry that is not digest-addressed. Range reads bypass the cache. Expired entries are purged by the federation worker; GC collects their blobs (cache rows are GC roots while they exist).
- **Configuration** (authority, part of the signed topology): `PUT /api/v1/federation/feeds/{fed}/{slug}/routing {"mode":"proxy|redirect|off","blob_urls":false,"cache":false,"cache_ttl_seconds":0,"max_lag_seconds":0,"prefer":["site"]}`, or `routing` when creating the feed key. No routing means proxy.
- **Explain:** `GET /api/v1/federation/routes/{fed}/{slug}` on any member (instance read) shows the decision and every candidate with role, replica state, circuit, RTT, preference and order. `GET /api/v1/feeds/{id}/resolve` adds the same plan as `federation` for a bound feed (instance readers only) and reports `status: federated` when a local miss would be routed. Console: Federation page, Federated feeds, "Read routing" (Explain, and Edit on the authority); Feeds, Resolve a package.
- **Responses** carry `X-Kuvryn-Route: proxy; member=<name>`, `redirect; member=<name>`, `blob_url; member=<name>` or `cache`.
- **Limits:** every routed read is charged to a per-principal token bucket on the entry member (50/s, burst 100; anonymous callers per client address; `429 route_rate_limited`). Proxied reads share the holder listener's per-member budget of signed requests (100/s, burst 200, and the request nonce cache) and a per-(entry member, principal) rate on the holder (50/s, burst 100; the same limit applies to blob URL reads); an entry member over either gets `429` and tries the next candidate, then answers `503 route_rate_limited`. Proxied-read assertions (GET and HEAD only) are replay-checked in an in-memory cache instead of `federation_assertion_nonces`, which mutations and every other assertion use: they are idempotent reads only the issuing member can send over its mTLS identity, a read must not cost a database write, and writes are never routed. The cache holds at most 65,536 unexpired records per issuing member, so a member over its quota is answered `429` alone and never affects the reads other members proxy.
- **Metrics:** `ant_federation_route_requests_total{mechanism,outcome}`, `ant_federation_proxy_bytes_total`, `ant_federation_proxy_active`, `ant_federation_route_served_total`, `ant_federation_route_served_bytes_total`, `ant_federation_route_writes_not_routed_total`, `ant_federation_route_cache_total{event=hit|store|drop}`, `ant_federation_blob_urls_total{event}`, `ant_federation_route_circuits_open`. Audit adds `federation.feed.routing_updated`; holders record the asserted caller like other assertions (`federation.assertion.accepted`, sampled).

## Authority operations, audit and pruning (P2-M6)

Step-by-step procedures and alerts: [federation-runbooks.md](federation-runbooks.md). This section is the reference.

- **Epochs.** The authority role has an epoch. Every document carries it, and every epoch key is certified by the previous epoch's key (planned handover) or by the offline recovery key (forced recovery); the member that becomes authority also signs an acceptance of the role with its own member key, so nobody can appoint a member that did not agree. Members accept the highest epoch whose chain verifies back to the pinned recovery key; a document of a lower epoch is rejected as `stale_epoch`. `GET /api/v1/federation/authority` shows the epoch history (authority, certification, first generation), this instance's role, a handover in progress, the fence record of a former authority and the recovery-key drill state. Metric `ant_federation_authority_epoch`, `ant_federation_authority` (1 on the authority); audit `federation.authority.handover_started|handover_prepared|handover_aborted|recovery_template|recovered|epoch_changed|fenced`.
- **Planned handover.** `POST /api/v1/federation/authority/handover {"to_member_id":…,"confirm":true}` on the authority. The target generates its own epoch key and returns only the public key; the current authority certifies it with its epoch key and sends the federation CA key (the new authority must keep issuing certificates) over the mutually authenticated channel; the target publishes the first document of the next epoch signed by its new key. The old authority applies it, deletes its authority and CA keys and becomes a member. Refused while a feed home transfer is active or when the target has not applied the latest membership, policy and topology (`409`). Publishing on the old authority is paused from the start (10 minutes at most; `POST …/authority/handover/abort` clears it).
- **Forced recovery.** On the member that takes over: `POST …/authority/recovery-template` (creates the pending authority key), sign the template offline with `ant federation recovery sign-authority-cert`, `POST …/authority/recover` with the signed certificate and `confirm: true` (optionally `remove_previous_authority`). The member creates a new federation CA, keeps presenting its existing listener certificate until it renews, and publishes the first document of the next epoch; both CAs are trusted until a later recovery displaces the older. A returning old authority learns of the higher epoch from its peers (`detectFence`, and the sync of every member prefers a member that reports a higher epoch), replaces its voided generations, deletes its keys and raises `authority_fenced`.
- **Recovery-key drill.** `POST …/recovery-key/challenge` (authority) and `POST …/recovery-key/verify` with the offline signature (`ant federation recovery sign-challenge`) record that the key is held. Alert `recovery_key_unverified` after 180 days (30 days after founding if never done).
- **Two-phase join.** A join claims the invitation (state `claimed`, held for the joining instance for 10 minutes) and adds the member; the joiner verifies the answer and confirms with a statement signed by its member key (`POST /federation/v1/join/confirm`, a public route with the same per-IP limit as join), which consumes the invitation. An unconfirmed claim (relayed or interrupted join) is released: the authority removes the provisional member, revokes its certificate and the invitation is usable again (`federation.join.abandoned`). A joiner may pin the authority's certificate (`authority_cert_sha256`) so an interceptor never sees the secret.
- **Revocation pruning.** Revoked certificate serials stay in the membership document (limit 4096) only while the revoked certificate could still be valid: the authority publishes a pruned list once a serial is older than 32 days (certificates live 30), audited as `federation.certificate.revocations_pruned`, and prunes before a publication that would exceed the limit.
- **Federated audit.** `GET /api/v1/federation/audit?action=&prefix=&result=&from=&to=&members=&limit=&cursor=` returns the audit events of this member and of the other members newest first, fanned out like search (`POST /federation/v1/audit/query`, signed assertion of the caller, 1.5 s per member, concurrency 8, 20 requests per second per peer and per principal). Each member authorizes the asserted principal itself and requires instance administration there (the grant of `GET /api/v1/audit`): federated administrator grants are inert on a member until `accept_admin_grants`, so such a member is reported `forbidden` (`audit_read_denied`) and the answer `partial`. Local principals get `403 not_federated`. Pagination keeps one `(created_at, id)` watermark per member inside an authenticated cursor. Each member's events carry that member's own principal IDs. MCP: `federated_audit`; console: Federation, "Federated audit".
- **Member health.** `ant_federation_member_up{member}`, `ant_federation_member_rtt_seconds{member}`; alert `member_unreachable` when an active member has not answered a status ping for 15 minutes (critical after 24 h). `explain_route` (MCP) is `GET /api/v1/federation/routes/{fed}/{slug}`.
- **Console and MCP.** The Federation page has "Authority" (epochs, handover with a typed confirmation, forced recovery and drill as copy-and-paste steps; the console never sees the recovery key) and "Federated audit". MCP adds `get_federation_authority`, the destructive `handover_federation_authority`, `federated_audit` and `explain_route`.
- **Compatibility.** Migration `038_federation_operations.sql` is additive. Joiners that predate the confirmation are removed after 10 minutes by a new authority; joiners from this release treat a `404` on the confirmation of an older authority as already consumed.
