# MCP tools

Kuvryn Ant embeds a [Model Context Protocol](https://modelcontextprotocol.io/) server, so AI assistants and other MCP clients can inspect and operate an instance with the same permissions as a service token. Implementation: [`internal/mcp`](https://github.com/azrtydxb/Kuvryn-Ant/blob/main/internal/mcp/README.md).

## Endpoint and transport

| Item              | Value                                                                                                            |
| ----------------- | ---------------------------------------------------------------------------------------------------------------- |
| URL               | `POST https://ant.example.com/mcp`                                                                               |
| Transport         | Streamable HTTP, JSON-RPC 2.0, stateless, JSON responses. `GET` answers 405: no SSE stream, no sessions          |
| Protocol versions | `2025-06-18`, `2025-03-26`, `2024-11-05` (an unsupported `MCP-Protocol-Version` header is rejected with 400)     |
| Content type      | `application/json` (415 otherwise); request body up to 1 MiB; JSON-RPC batches are accepted                      |
| Methods           | `initialize`, `ping`, `tools/list`, `tools/call`, `resources/list`, `resources/templates/list`, `resources/read` |
| Server info       | `{"name":"kuvryn-ant","title":"Kuvryn Ant"}`                                                                     |

## Authentication and authorization

- `/mcp` requires `Authorization: Bearer <TOKEN>` with a **service token** (`ant_...`), the same credential as the management API. Browser sessions and personal access tokens are not accepted. Failed authentication is rate limited like the management API.
- Requests with an `Origin` header whose host differs from `Host` are rejected (403), so a web page cannot drive the server from a browser.
- No tool contains its own SQL or authorization. Each tool calls the management API handler in-process with the caller's `Authorization` header, so authorization, validation, idempotency and audit are exactly those of the HTTP API: a token the API denies is denied identically through MCP. Token scopes and [role grants](../identity/roles.md) apply as usual, so a read-only token gives a read-only MCP server.
- Every `tools/call` and `resources/read` also writes an `mcp.tool.call` or `mcp.resource.read` audit event (tool name, outcome, HTTP status, token ID, target UUID; never arguments or results). If that audit write fails, the result is withheld.

Create a dedicated service account and token with the narrowest scopes that cover what the assistant should do (see [Service accounts and tokens](../identity/tokens.md)).

## Tool conventions

- **Kinds.** `read` tools are annotated `readOnlyHint: true`. `write` tools change state. `destructive` tools are annotated `destructiveHint: true` and refuse to run unless the call passes `confirm: true` (JSON-RPC error `-32602` otherwise); refusals are audited with outcome `confirmation_required`.
- **Idempotency.** Every non-read tool accepts an optional `idempotency_key` (1 to 256 bytes) that makes retries replay-safe; one is generated when omitted.
- **Revisions.** Tools that take `revision` send it as `If-Match`; when omitted, the current revision is read first.
- **Dry runs.** `start_retention_run` and `start_storage_job` default to `dry_run: true`.
- **Errors.** Protocol and argument errors are JSON-RPC errors (`-32700`, `-32600`, `-32601`, `-32602`, `-32603`). API failures (denied, not found, conflict) are tool results with `isError: true` carrying only the API's stable `code`, `message` and `request_id`.

| --------------------------- | ------------------------------------------------------------------------------ |

All resources are `application/json` and go through the same authorization as the tools.

## Client configuration

Any client that supports the Streamable HTTP transport with custom headers works.

::: code-group

```json [Claude Code (.mcp.json)]
{
  "mcpServers": {
    "kuvryn-ant": {
      "type": "http",
      "url": "https://ant.example.com/mcp",
      "headers": { "Authorization": "Bearer ${ANT_TOKEN}" }
    }
  }
}
```

```sh [Claude Code (CLI)]
claude mcp add --transport http kuvryn-ant https://ant.example.com/mcp \
  --header "Authorization: Bearer $ANT_TOKEN"
```

```json [Generic MCP client]
{
  "servers": {
    "kuvryn-ant": {
      "type": "http",
      "url": "https://ant.example.com/mcp",
      "headers": { "Authorization": "Bearer <TOKEN>" }
    }
  }
}
```

:::

The exact key names (`mcpServers`, `servers`) depend on the client; the essentials are the URL, HTTP transport and the `Authorization` header.

## Smoke test

```sh
curl -fsS https://ant.example.com/mcp -H "Authorization: Bearer $ANT_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":1,"method":"tools/list"}' | jq '.result.tools[].name'

curl -fsS https://ant.example.com/mcp -H "Authorization: Bearer $ANT_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":2,"method":"tools/call","params":{"name":"list_feeds","arguments":{"limit":10}}}' | jq
```

A destructive call without confirmation is refused:

```sh
curl -fsS https://ant.example.com/mcp -H "Authorization: Bearer $ANT_TOKEN" \
  -H 'Content-Type: application/json' \
  -d '{"jsonrpc":"2.0","id":3,"method":"tools/call","params":{"name":"revoke_service_token","arguments":{"token_id":"<UUID>"}}}'
# -> JSON-RPC error -32602 "... is destructive: pass confirm: true to proceed"
```
